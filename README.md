# GitHub 협업 실습실

`lab.html`에서 나와 지수(가상 인물)가 백설공주 이야기를 수정합니다. **나는 수정과 충돌 해결, 지수는 모든 PR의 검토·승인·병합**을 맡습니다. 실제 프로젝트에서는 여러 사람이 이 역할을 나눌 수 있습니다.

## 세 실습 탭

- **2D 협업지도**: 저장소 복제 → 브랜치 → 파일 수정 → 기록 → 공유 → PR → 지수의 수정 의견 → 재수정 → 지수의 승인·병합 → 각자 받아오기.
- **이슈/충돌 실습**: 두 이슈를 내게 할당 → 두 작업 브랜치와 PR → 지수의 검토·병합 → 충돌 비교 → 두 내용을 합친 해결 문장 → 해결 기록 → 지수의 재검토·병합.
- **협업+이슈/충돌 실습**: 이슈 할당부터 첫 PR의 수정 의견 반영과 두 번째 PR의 충돌 해결까지 같은 저장소에서 이어갑니다. 앞 실습을 끝낸 뒤 다른 예제로 초기화하는 방식이 아닙니다.

세 탭은 진행 상태를 따로 보관합니다. 3D 참고 화면은 제거했습니다.

## 화면과 실제 상태

처음에는 GitHub 저장소에만 기록 B가 있습니다. 내 컴퓨터와 지수의 컴퓨터에는 프로젝트 폴더와 `.git` 폴더가 없습니다. 각자 **저장소 복제하기**를 실행한 뒤에만 로컬 파일과 기록이 나타납니다.

B, C, D 등은 파일명이 아니라 기록 이름입니다. 기록을 누르면 당시 `snow-white.md` 내용을 볼 수 있습니다. 브랜치는 기존 기록을 가리키는 이름이며 별도 폴더를 만들지 않습니다.

본문 수정과 지수 의견 반영은 각각 한 가지 문장으로 진행합니다. 문장을 고르는 선택지는 없습니다. 파일 수정 창에는 수정 전·저장할 문장과 **이 문장 저장하기** 버튼만 있습니다.

## 역할과 충돌

두 PR 모두 내가 서로 다른 브랜치에서 작성합니다. 지수는 PR을 작성하지 않으며 모든 검토와 병합을 맡습니다. 지수가 자신의 PR을 승인하는 상황은 없습니다.

이슈 할당은 담당자 배지가 이슈에 붙는 모습으로 표시합니다. 할당만으로 파일이나 브랜치는 생기지 않습니다. 충돌 장면은 공통 시작 기록, 현재 기준본, 남은 PR의 같은 줄을 나란히 보여 줍니다. 두 부분을 합친 문장을 적용한 뒤 해결 기록 R을 별도로 만듭니다.

해결은 GitHub 편집기에서 진행하는 사례입니다. R은 GitHub의 작업 브랜치에만 생기고, 지수가 다시 승인해야 합칠 수 있습니다. 각 컴퓨터는 병합 후 기준본을 별도로 받아옵니다. 이슈는 PR의 `Closes #번호` 연결에 따라 병합 시 닫힙니다.

## 변경 설명과 탐색

동작마다 복사·할당·병합 과정을 애니메이션으로 보여 줍니다. **변경 설명 카드는 자동으로 닫히지 않습니다.** 충분히 읽은 뒤 **확인하고 계속**을 누릅니다. `Esc`로 닫는 것도 같은 확인 동작입니다. **변화 다시 보기**는 상태를 바꾸지 않고 설명을 다시 표시합니다. 모션 감소 설정에서도 카드는 유지됩니다.

이전 단계와 다시 앞으로는 방문한 학습 상태를 복원합니다. 실제 Git 기록을 삭제하는 동작은 아닙니다. 이전 단계에서 새 동작을 하면 그 이후 진행 결과를 다시 만듭니다. 새로고침하면 모든 실습이 초기화됩니다.

## 실행

Node.js 20 이상에서:

```sh
npm start
```

`http://localhost:4173/lab.html`을 엽니다. 서버는 정적 파일만 제공합니다. 로그인, 방 만들기, 실시간 다중 접속은 없습니다. 실제 GitHub 저장소를 변경하지 않습니다.

정적 호스팅에는 `lab.html`, `lab.js`, `lab.css`, `workshop-model.mjs`, `workshop-ui.mjs`, `workshop-motion.mjs`와 서체·브랜드 이미지가 있는 `assets/`를 포함합니다. JavaScript 모듈 때문에 `file://` 대신 HTTP로 실행해야 합니다. WebGL이나 Three.js는 사용하지 않습니다.

## 검증

```sh
npm test
```

복제 전 로컬 부재, 고정된 한 가지 수정안, 저장·기록·공유 구분, 지수의 검토·병합, 충돌 해결 후 재승인, 각자의 받아오기, 통합 실습의 기록 연속성과 이전·다음 상태 복원을 검사합니다. 브라우저에서는 설명 카드 유지, 세 탭의 독립 상태, 파일 수정 창과 시각적 할당·충돌 장면을 확인합니다.

## 사용 방법

- 이전·다음: 화면 버튼, 좌우 방향키, PageUp·PageDown
- 첫 장·마지막 장: Home·End
- 발표자 노트: 화면 버튼 또는 N, 닫기: Esc
- 발표·세로 읽기 전환: 화면 버튼 또는 R
- 전체화면: 화면 버튼, 해제: Esc
- 인쇄: 화면 버튼 또는 브라우저 인쇄 메뉴
- 흑백: 흑백 버튼 선택 후 인쇄

좁은 화면이나 세로 화면은 읽기 모드로 시작합니다. 넓은 표는 표 영역을 가로로 스크롤해 확인할 수 있습니다. 모바일에서 인쇄하려면 브라우저 메뉴를 사용합니다. 인쇄 시 브라우저의 머리글·바닥글을 끄고, 색상 보존을 위해 배경 그래픽을 켭니다. 인쇄 페이지는 16:9 가로, 슬라이드당 한 페이지입니다.

## 시각 자료와 데모

- 2장: 같은 FAQ 파일의 수정 전·후 비교
- 4·8·12장: 실제 GitHub 공개 화면의 고해상도 확대 캡처
- 9장: 작업 브랜치 분기·commit·merge 데모
- 10장: 저장·staging·commit 데모
- 11장: Push 한 번의 실행 전·후 비교, main 유지 확인
- 15장: Pull 한 번의 실행 전·후 로컬 main 비교
- 21장: 30초 MP4 협업 흐름 영상, 무음·한국어 설명 자막

데모의 ‘재생’, ‘다음 단계’, ‘처음’ 버튼으로 조작합니다. 슬라이드를 넘기면 영상과 데모 재생이 멈춥니다. 인쇄에서는 영상 포스터와 데모의 정지 화면을 표시합니다. 좁은 화면의 도식은 영역 안에서 가로 스크롤할 수 있습니다.

실제 화면은 GitHub 공개 저장소 [github/docs](https://github.com/github/docs)와 [PR #45779](https://github.com/github/docs/pull/45779), [변경 비교](https://github.com/github/docs/pull/45779/files)에서 2026-09-08에 캡처한 발췌입니다. 해당 PR은 교육용 FAQ 예시와 별개의 실제 사례입니다. 당시 화면을 그대로 사용하며 이름·상태·코드의 합성 변경은 없습니다.

`demo.js`의 조작형 도식과 `assets/demo/workflow-captioned.mp4`는 이 자료를 위해 제작한 교육용 시뮬레이션입니다. 실제 GitHub 조작을 녹화한 영상과 구분합니다. 각 점은 기록된 버전을 뜻하며 라임색 점은 FAQ 변경의 기록입니다. 상세 개념은 발표자 노트와 원고를 참고합니다.

추가 파일: `demo.css`, `demo.js`, `assets/screens/`, `assets/demo/`. 영상에는 한글 설명이 화면에 포함되어 있으며 별도 자막 파일 `workflow.ko.vtt`도 제공합니다.

Push·Pull 비교 화면은 별도 작업 단계를 나열하지 않고, 한 명령을 실행하기 전과 실행한 후의 상태를 표시합니다. ‘Push 실행 보기’·‘Pull 실행 보기’는 슬라이드 안의 시뮬레이션 버튼으로, 실제 저장소를 변경하지 않습니다.

21장 영상의 6개 단계에 한국어 설명 자막을 직접 포함했습니다. CC 설정이나 별도 자막 파일 로딩 없이 표시됩니다. `assets/demo/workflow-captioned.mp4`를 단독 재생해도 자막이 보이며, 편집용 `workflow.ko.vtt`도 동봉합니다.

## GitHub Pages 배포

`main` 브랜치의 저장소 루트에서 배포합니다. `.nojekyll`로 정적 HTML·CSS·JavaScript와 미디어 파일을 그대로 게시합니다. `main`에 변경을 push하면 GitHub Pages가 사이트를 갱신합니다.
